## What ran

The shipped `openclaw daemon install` CLI command (`node --import tsx src/entry.ts daemon install --allow-unconfigured --json`) runs on a macOS-14 runner through the real Gateway install pipeline: `runDaemonInstall → installLaunchAgent → bootstrapLaunchAgentOrThrow`. A real `launchctl` child process handles every command except `bootstrap`, which the ESM loader forces to return a genuine EIO ("Bootstrap failed: 5: Input/output error") that `isLaunchctlBootstrapPendingTeardown` classifies as pending teardown — reproducing a bootout racing the next bootstrap. The monotonic clock (`performance.now` / `setTimeout`) is real throughout.

- **OLD variant:** the loader reverts `launchd-runtime.ts` to `Date.now()` for the deadline seed and `Date.now() + WALL_JUMP_MS` for the remaining-budget read, so a wall-clock step lands between seed and read (the buggy arithmetic this PR fixes).
- **FIXED variant:** the loader leaves `performance.now()` untouched (the PR's monotonic deadline).

## Interpretation

- **OLD forward +1,000,000 ms:** the wall-clock deadline seed is `Date.now()`, the remaining read is `Date.now() + 1e6`, so `remainingMs` drops to `<= 0` as soon as the retry loop reaches its first remaining-budget check. The shipped CLI reports `ok: false` after 22s (most of which is CLI startup + plist write + enable; the deadline fires immediately once `bootstrapLaunchAgentOrThrow` is reached).
- **FIXED forward +1,000,000 ms:** the deadline is `performance.now()` (monotonic), immune to the wall-clock step. The retry loop honors the full `LAUNCH_AGENT_BOOTSTRAP_TEARDOWN_TIMEOUT_MS` (~340s) before the deadline fires — 354714ms elapsed, matching the intended bounded budget.
- The 22s vs 355s gap is the bug: OLD's wall-clock deadline is truncated by the forward jump; FIXED's monotonic deadline is not.
